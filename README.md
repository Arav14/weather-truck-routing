# Weather-Aware Truck Routing

React + Django app that compares three driving routes for a truck and recommends the safest one using
forecast weather **at the time the truck will actually be there**, the load weight, and travel time.

**Live demo:** https://weather-truck-routing-eiy2.onrender.com/

> Hosted on Render's free tier, so the first load after a period of inactivity can take 30–60 seconds to wake up.

## Run locally

```bash
# backend (http://127.0.0.1:8000)
cd backend && python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python manage.py test          # risk rules, ranking and API validation (offline)
python manage.py runserver

# frontend (http://localhost:5173, proxies /api to Django)
cd frontend && npm install && npm run dev
```

No API keys are needed. Providers: **Photon** (geocoding), **OSRM** (routing), **Open-Meteo** (hourly wind, rain, snowfall).

## Deploy (one container, Django serves the built React app)

`docker build -t truck-routing . && docker run -p 8000:8000 -e DJANGO_SECRET_KEY=change-me truck-routing`

On Render/Railway/Fly: create a Docker web service from this repo and set `DJANGO_SECRET_KEY`. Nothing else is required.

## How it works

1. **Routes** – OSRM returns up to 3 alternatives. If it returns fewer, extra routes are generated by routing via a
   waypoint pushed sideways off the main route, and kept only if they differ meaningfully (<85% overlap, <1.8x length).
   Routes are labelled A, B, C by travel time.
2. **Checkpoints & ETAs** – each route is sampled every 10 / 25 / 50 miles (your choice). ETA = departure + route
   duration × fraction of distance covered (constant average speed).
3. **Weather** – one batched Open-Meteo call per ~50 points covers departure through the last ETA (and at least 48h).
   Each checkpoint uses the forecast hour nearest its ETA: sustained 10 m wind (mph), rain and snowfall (in/hr).
4. **Risk** (`backend/routing/risk.py`) – each condition is classified with the brief's thresholds; the checkpoint takes
   the worst one, then the load rules apply (≥55 mph No Travel; 45–54 mph + >30,000 lb No Travel; 35–44 mph + >40,000 lb Severe).
   Shared band edges: wind uses `<35`, `<45`, `<55`; rain/snow edges are upper-inclusive (rain 1.00 = Severe, >1.00 = No Travel).
5. **Route metrics** – each checkpoint owns the road halfway to its neighbours, so Severe/High miles are real
   mileage, and average risk (0–4) is mileage-weighted.
6. **Recommendation** (`analysis.py`) – lexicographic: fewest Severe miles → fewest High miles → lowest average risk →
   shortest time. Two judgement calls: No Travel miles rank first (an undrivable route can't win), and differences
   under 5 miles / 0.1 risk count as ties, otherwise exact-float comparisons would mean travel time never matters.
   The UI shows the reason the winner won.
7. **Heatmap** – every checkpoint also gets its risk level for each of the 49 hours after departure (0–48h).
   The slider only redraws one canvas layer, so scrubbing is instant with no network calls.

## Known limitations

- OSRM's public server uses a car profile; truck restrictions (height, hazmat, weight limits) are not modelled.
  Set `TRUCK_TIME_FACTOR` (e.g. `1.15`) to slow ETAs, or point `OSRM_URL` at your own OSRM/ORS instance.
- Public Photon/OSRM/Open-Meteo endpoints are rate limited and meant for light use; results are cached in memory
  (weather for 30 min, geocoding for 24 h).
- Departure must be within 24h ago to 14 days ahead (the forecast range).
- ETAs use constant average speed, not per-segment speeds or driver hours-of-service breaks.
